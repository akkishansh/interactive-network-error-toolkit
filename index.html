Four Error-Control Methods

① Parity · Count the 1s

Add one bit so the total number of 1s is even. The receiver counts again. It is simple, but an even number of flips can go unnoticed.

Useful as a simple, low-cost check for single-bit errors in basic links or memory.

② Checksum · Add small pieces

Add bytes, fold the carry, and attach the inverted sum. The receiver repeats the arithmetic. Some different changes can cancel each other out.

Analogy: checking that the line items on a bill add up to the total.

③ CRC-8 · Divide by a fixed pattern

The sender and receiver use the same generator bit pattern. The remainder is the check value. CRC detects many accidental error patterns, but it does not repair data.

Analogy: a seal designed to reveal many kinds of accidental damage.

④ Hamming (7,4) · Locate and correct one bit

Each group of 4 data bits gets 3 check bits. Failed checks form a syndrome that identifies a bit position. The receiver flips that bit in its local copy.

A supported single-bit error can be corrected without retransmission. The receiver still calculates the syndrome and corrects its local copy.
What this model covers: This app uses small teaching versions: parity, an 8-bit checksum, CRC-8, and Hamming (7,4). Ethernet uses CRC-32; TCP and UDP use 16-bit checksums. See the Real-World Protocols tab for details.

REAL-WORLD NETWORKING · SIMPLIFIED

How real protocols handle errors and security

These four methods teach the core ideas. Real networks combine error checks, delivery mechanisms, and security. A checksum or CRC detects many accidental changes; it does not encrypt data or verify the sender’s identity.

LINK / FRAME

Ethernet · CRC-32 FCS

Ethernet appends a Frame Check Sequence (FCS) to each frame. Its CRC-32 detects many accidental bit errors. A frame that fails the check is discarded; CRC does not repair it.

Parcel analogy: a damage-detecting seal. If the check fails, the frame is discarded; a higher layer may arrange another send.
TRANSPORT

TCP · checksum + sequence numbers + ACKs

TCP calculates a 16-bit one’s-complement checksum over a pseudo-header, header, and data. Sequence numbers and acknowledgements track received data; retransmission recovers missing segments. The checksum does not repair corrupted data.

Tracked delivery: each part is numbered; the receiver reports what arrived; the sender resends missing data.
TRANSPORT

UDP · checksum without TCP's delivery guarantee

UDP uses a checksum to detect errors. IPv4 permits a zero checksum in limited cases; IPv6 generally requires one. UDP itself does not guarantee delivery, ordering, or retransmission. An application can add those features.

Quick postcard: the receiver can check for damage, but the service does not promise to resend a lost postcard.
SECURITY

TLS 1.3 · authenticated encryption (AEAD)

TLS 1.3 uses authenticated encryption with associated data (AEAD) to encrypt records and verify an authentication tag. A record that fails authentication is rejected. This keyed cryptographic protection is different from CRC or parity.

Locked, tamper-evident parcel: outsiders cannot read the contents, and a change fails the keyed seal check.

How can a transmission error occur in a real network?

A network sends bits as electrical, optical, or radio signals. The receiver measures each signal and interprets it as a 0 or 1. Noise, interference, a weak signal, damaged cables or connectors, or timing problems can distort the signal or prevent it from being read correctly. These errors are usually accidental; they do not imply that someone deliberately changed the message.

Real transmission: Application message → bytes and bits → electrical, optical, or radio signals → channel → receiver interprets the signals → integrity check → damaged frame is discarded or a higher-level protocol attempts recovery.
Our simulation: Enter a message → encode its bits and check value → click a bit to deliberately flip 0 ↔ 1 → run the receiver check → inspect detection or correction. The app changes the bit directly; it does not model physical signals, interference, cables, or network hardware.
Why does this toolkit use simplified methods? Each model isolates one idea: parity uses counting, checksum uses addition, CRC uses polynomial division, and Hamming demonstrates error correction. Small examples make each bit visible. The CRC-8 in this app is for teaching; it is not the CRC or checksum used by TCP, UDP, Ethernet, or TLS.
